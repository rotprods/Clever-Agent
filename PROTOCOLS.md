# PROTOCOLS — Clever-Agent multi-agent development operating system

## 1. Purpose

These protocols make repository state — not an individual chat or agent — the durable operating system for Clever-Agent.

Core properties:

- resumable by a fresh agent;
- safe for multiple parallel agents;
- evidence-backed checkpoint progression;
- deterministic ownership and handoff;
- no silent capability loss;
- no irreversible action by momentum or assumption.

---

## 2. Project boot protocol

Every material session starts with `/empezarproyecto` (`commands/EMPEZARPROYECTO.md`).

The boot process produces a ContextPack:

```text
project_id
goal_id
branch/worktree/session
active_checkpoint
active_iteration
candidate_wave
owned_paths
dependencies
open_decisions
open_risks
required_evidence
latest_handoff
validation_status
```

A session that cannot derive a consistent ContextPack is in RECONCILIATION mode, not implementation mode.

---

## 3. Wave protocol

### Definition

A `/wave` is a transaction-sized engineering mission.

Required fields:

```text
wave_id
checkpoint_id
iteration_id
objective
owner/session
owned_paths_or_surfaces
inputs/dependencies
acceptance_criteria
test_plan
evidence_plan
risk_delta
status
```

### Lifecycle

1. `PROPOSED` — slice defined.
2. `CLAIMED` — ownership registered, conflict check passed.
3. `IN_PROGRESS` — material mutation allowed.
4. `VERIFYING` — implementation frozen except verification fixes.
5. `COMPLETE` — criteria + tests + evidence + persistence satisfied.

Exceptional:

- `BLOCKED` — external/technical blocker reproduced and persisted.
- `ABORTED` — slice intentionally stopped before accepted implementation.
- `ROLLED_BACK` — implemented slice reverted due to regression/risk.

### Completion rule

A wave is not complete until code/docs + tests + evidence + ledgers + state/handoff agree.

---

## 4. Claim and lease protocol

Claims prevent two agents from silently editing the same authoritative surface.

- Record claims in `ledgers/CLAIM_LEDGER.ndjson`.
- Prefer non-overlapping path ownership.
- Interface changes require explicit coordination between producer/consumer waves.
- Agents heartbeat long-running claims through the run/claim ledgers.
- A stale claim can be superseded only after checking branch/PR activity and logging the supersession.
- Never resolve a claim collision by deleting another agent's branch/worktree or force-updating its history.

For high-contention files (`AGENTS.md`, `GOAL.md`, `STATE.md`, checkpoint/state JSON, shared schemas), use a single active writer at a time.

---

## 5. Live-truth/reconciliation protocol

Truth precedence:

1. merged Git + evidence generated by that Git;
2. machine checkpoint/state records;
3. `STATE.md` human pointer;
4. `HANDOFF.md`;
5. append-only logs for chronology;
6. chat context.

If two sources disagree:

1. do not guess;
2. inspect Git/evidence;
3. create a reconciliation wave when material;
4. record the decision;
5. update all mutable mirrors atomically in one coherent commit.

---

## 6. Persistence protocol

Persist before exit after every material delta to:

- implementation/documentation;
- checkpoint or wave state;
- discovered capability;
- decision;
- blocker/risk;
- evidence;
- upstream drift;
- task ownership.

Required event principle: an agent may disappear immediately after its response and the repository must still expose the next valid action.

---

## 7. Handoff protocol

A handoff is operational state transfer, not a narrative summary.

Required:

```text
session_id / wave_id
branch / commit / dirty state
checkpoint / iteration
files/surfaces changed
acceptance criteria status
tests and exact evidence locations
decisions and risk changes
claims still held or released
blockers
exact next frontier
first recovery commands/files
```

The receiver validates the handoff during `/empezarproyecto`.

---

## 8. Checkpoint protocol

Global checkpoint state lives in `CHECKPOINT_REGISTRY.json`; `CHECKPOINTS.md` is the human-readable map.

Rules:

- no skipping dependency gates;
- no advancement from percentage intuition;
- no checkpoint closure with unpersisted test output;
- checkpoint state changes happen in the same wave/commit as the evidence/ledger reconciliation that proves them;
- any exclusion from capability parity needs an explicit waiver.

---

## 9. Gauntlet protocol

Every significant wave has an adversarial review proportional to risk.

Minimum questions:

- What capability could this silently delete or misclassify?
- Can state become false-green?
- What happens on retry/process death/network/provider failure?
- Can untrusted content cross a permission boundary?
- Can evidence claim success without exercising behavior?
- Can another runtime/version interpret the contract differently?
- What is the rollback/recovery path?

CP01 additionally asks: **what source surface did the inventory compiler fail to discover?**

---

## 10. Test protocol

Testing pyramid for this repository:

1. schema/static validation;
2. unit tests;
3. contract tests;
4. integration tests;
5. upstream parity/baseline tests;
6. E2E scenarios;
7. security/adversarial tests;
8. recovery/failure injection;
9. performance/energy/cost where relevant.

A wave runs only the layers relevant to its risk/surface, but checkpoint closure runs the full required gate set.

---

## 11. Decision protocol

Material architecture, scope, parity, security or persistence decisions receive stable IDs in `ledgers/DECISION_LEDGER.ndjson`.

A decision records:

- ID/date;
- context;
- decision;
- alternatives rejected;
- consequences;
- affected invariants/checkpoints;
- evidence/ADR link when applicable.

Do not bury irreversible architecture decisions only in commit messages.

---

## 12. Risk protocol

Risks live in `ledgers/RISK_LEDGER.ndjson` with status `OPEN | MITIGATED | ACCEPTED | CLOSED`.

A wave touching a known risk must update its record or explicitly state no risk delta.

Security/privacy risks cannot be silently accepted by an implementation agent.

---

## 13. Git/PR protocol

- Branch/worktree per material wave where practical.
- PR describes checkpoint/wave, acceptance criteria, tests/evidence, parity delta and risk delta.
- No unrelated cleanup.
- No force-push to `main`.
- Merge only after state validator and relevant tests pass.
- `main` is the durable integration point; personal worktrees are disposable compute surfaces.

---

## 14. Repository start/resume commands

Canonical command family:

- `/empezarproyecto` — boot, reconcile, recover frontier, claim next wave.
- `/wave` — define/claim a coherent vertical slice.
- `/checkpoint` — evaluate current checkpoint against evidence; never auto-advance from prose.
- `/gauntlet` — adversarially attempt to falsify the current completion claim.
- `/handoff` — persist operational transfer state.
- `/reconcile` — resolve drift among Git/state/evidence/ledgers.
- `/closewave` — verify, persist, release claims and hand off.

These are semantic protocols; individual coding environments may implement them as slash commands, prompt files or agent skills.
